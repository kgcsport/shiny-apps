Building Real Multiplayer Classroom Games

The Game Builder's one-screen and GameSync modes handle most classroom needs. This guide is for when you want something more powerful: a game with persistent data, private per-student information, instructor controls, or custom logic — the kind of thing you'd build for a full semester. You don't need to be a software engineer. AI does most of the coding. Your job is to design the game.

See a real example first

The Classroom Economy is a full server-coordinated app built for this course. It runs a token economy across an entire semester: students earn tokens through jobs and participation, spend them on grade bonuses and exam passes, and compete in multi-round classroom markets. Everything is tracked in a database and survives between sessions.

What you actually need

The minimum to build and run a server-coordinated classroom game is surprisingly small. Here's an honest breakdown of what's required versus what's optional:

ComponentRequired?What it does
Node.jsRequiredRuns your game server. Free, installs in 2 minutes.
SQLite databaseRequiredStores student data, balances, submissions. Comes bundled with the repo — no separate install.
WebSocketsRequired for live syncPushes updates to all students' browsers in real time. Already wired up in the template.
A server / VPSRequired for class useStudents need a URL to connect to. A $6/mo VPS (DigitalOcean, Hetzner) works fine. You can develop locally first.
HTTPS / nginxOptionalNeeded if students will connect over the public internet (browsers block mixed content). Not needed for local development or a private campus network.
Google OAuthOptionalLets students log in with their .edu Google account. Convenient but requires a Google Cloud project. Alternatives: username/password, no login at all (just a name entry), or a shared class code.
DockerOptionalMakes deployment reproducible. Useful if you're sharing the app with someone else or running multiple apps on one server. Skip it when you're just getting started.
The simplest possible setup: run node server.js on your laptop, have students connect to your local IP on the campus network. No HTTPS, no OAuth, no Docker. Works fine for a single class session. Upgrade piece by piece as you need more.
1

Get the code from GitHub

Everything is in the open-source repository at github.com/kgcsport/shiny-apps. The Game Builder and all the classroom apps live here.

To get a copy on your computer:

# Install git if you don't have it: https://git-scm.com/downloads
git clone https://github.com/kgcsport/shiny-apps.git
cd shiny-apps

The Game Builder server is in apps/demo-kit-site/. The Classroom Economy is in apps/class-job-market/. When you build your own game, you'll copy the Game Builder folder and modify it.

Don't have git? You can also download the repo as a ZIP from the GitHub page (green "Code" button → "Download ZIP"). Extract it and you have the same files.
2

Run it on your computer first

Install Node.js (the LTS version). Then:

cd apps/demo-kit-site
npm install
node server.js

Open http://localhost:3000 in your browser. You now have a working Game Builder running locally — no internet connection required. The .env setup for Google OAuth and a live domain can come later.

To skip the login screen during development, set one environment variable before starting:

# Mac / Linux
DEMO_KIT_AUTH_DISABLED=true node server.js

# Windows (PowerShell)
$env:DEMO_KIT_AUTH_DISABLED="true"; node server.js
3

Design your game before writing any code

This is the step most people skip, and it's the one that matters most. Before you open a chat with AI, answer these questions on paper:

What decisions do students make?

Every good classroom game has a clear choice: submit a bid, choose a quantity, contribute tokens, accept or reject an offer. Be specific: what are the options, what are the constraints?

What information do they see?

Do students see each other's choices? Do they see aggregate information (class average, price level) but not individual choices? Does information reveal at the end of a round?

What does the instructor control?

Can you open and close rounds? Adjust a parameter mid-game? Reveal results manually? Kick a student?

What needs to persist between class sessions?

Token balances, cumulative earnings, grade data — anything that survives a browser refresh or server restart needs to go in the database. Anything that can reset each class session can live in memory.

Write a one-paragraph description

Once you can answer those questions, write a single paragraph describing the game as if you were explaining it to a student. That paragraph becomes your first AI prompt.

4

Work with AI to build it

AI (Claude, ChatGPT) can write the Express routes, SQL queries, WebSocket logic, and HTML front-end. Your job is to describe what you want clearly and review what it produces. Here's a workflow that works well:

Start with the database schema

Paste your one-paragraph description and ask AI to design the SQLite schema first. Review it before moving on — everything else will be built on top of it.

Example prompt: "I'm building a classroom double-auction market in Node.js + Express + SQLite. Students post bids (buy orders) and asks (sell orders) for a single good. The instructor opens and closes trading rounds. At the end of each round, clear the market: match the highest bid to the lowest ask, continue until no profitable trades remain. Design the SQLite schema for students, rounds, orders, and trades."

Build one route at a time

Don't ask for the whole app at once. Build one feature, test it, then add the next. A typical sequence:

  1. Student login (or just a name entry form)
  2. Student submits an action (POST route + database write)
  3. Instructor sees current submissions (GET route)
  4. WebSocket broadcast so students see live updates
  5. Instructor advances the round
  6. Results page

Paste the existing code when asking for changes

Always include the relevant section of server.js in your prompt. AI can't guess what you've already built — it needs to see it to extend it in the same style.

Example prompt for iteration: "Here's my current server.js [paste it]. I want to add a leaderboard endpoint that returns the top 10 students by cumulative earnings, ordered highest to lowest. Add the route and the SQL query."

Test with two browser tabs

Before involving students, open the game in two tabs — one as a student, one as the instructor — and walk through the full flow. Bugs in the game logic are much easier to fix before class than during it.

5

Choose how students log in (or don't)

You have several options, in order of complexity:

No login — just a name

Students type their name when they arrive. The server stores a session cookie. Works great for single-session games where you don't need to link data to a grade book.

app.post('/api/join', (req, res) => {
  const { name } = req.body;
  req.session.user = { name };
  req.session.save(() => res.json({ ok: true }));
});

Username + password you hand out

Give each student a username and password (or one shared class code). No Google project needed. You maintain a list of valid credentials in the database or a config file. Ask AI to write the login route.

Google OAuth (what the Classroom Economy uses)

Students log in with their .edu Google account. Requires setting up a free Google Cloud project and getting a client ID and secret (takes about 15 minutes, fully documented at developers.google.com). Provides real identity without managing passwords. The full implementation is already in apps/demo-kit-site/server.js — copy it.

6

Deploy so students can reach it (optional for now)

For a game that students access on their own devices from anywhere, you need a server with a public URL. The cheapest practical option is a VPS (virtual private server):

  • DigitalOcean Droplet — $6/mo, 1GB RAM, runs everything in this repo easily
  • Hetzner Cloud — €4/mo, slightly cheaper, European data centers
  • Render.com — free tier available, simpler than a raw VPS, but cold-start delays

Once you have a server, the basic deployment is:

# On your VPS
git clone https://github.com/kgcsport/shiny-apps.git
cd shiny-apps/apps/demo-kit-site
npm install
# Set your environment variables, then:
node server.js

For a permanent setup you'd use a process manager (pm2) so the server restarts automatically if the VPS reboots. Ask AI to write the pm2 config.

HTTPS (optional but recommended for production)

Browsers enforce HTTPS for pages that use certain APIs (camera, clipboard) and show a "not secure" warning on plain HTTP. If students will connect over the public internet, add HTTPS. The standard approach is nginx as a reverse proxy with a free Let's Encrypt certificate. Ask AI: "How do I set up nginx with a Let's Encrypt certificate to proxy to a Node.js app on port 3000?" It's about a dozen config lines.

Practical tips

  • Get the database schema right first. Once students have submitted data you don't want to throw it away. Think through what columns you need before the first class session that uses it.
  • One broadcast, one source of truth. Write a single broadcast() function that reads the current state from SQLite and sends it to every WebSocket client. Call it after every write. Don't try to send partial updates — just send everything every time. SQLite reads are fast enough for a class of 200.
  • Instructor view = query string check. ?admin=1 checked against a hardcoded admin email is enough. You don't need a separate login or role system to start.
  • SQLite is your friend. It's a single file. You can open it with DB Browser for SQLite to inspect or edit data directly, export to CSV, or fix a bug mid-semester. No database server to manage.
  • AI is better at code than at game design. Spend your time on the economics — what information, what choices, what incentives. The code is the easy part once you know what you're building.
  • Describe the existing code when asking for changes. Paste the relevant section of server.js into Claude and say exactly what you want to add. "Add a route that does X" works much better than "make the game have X."
Ready to start? Clone the repo, run the Game Builder locally, and ask Claude: "I want to build [describe your game]. Here's the existing server.js structure [paste it]. Design the SQLite schema and the first two API routes."
