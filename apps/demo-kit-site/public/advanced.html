Building Real Multiplayer Classroom Games

The Game Builder's built-in multi-device mode (GameSync) handles simple public-state games in minutes. This guide is for the next step: games that need per-student private state, persistent data between sessions, admin controls, and full server logic — like the Classroom Economy app.

When GameSync is enough

GameSync (used by the Game Builder's Multi-device ⚡ mode) is a thin WebSocket layer that syncs a single shared object across all connected browsers. It's ideal when:

  • All players see all of each other's moves in real time
  • State can reset between class sessions without loss
  • The game logic lives entirely in the browser
  • No player needs to keep information secret from others

Examples that fit well: contribution games, live polls, public auctions, coordination problems, simple round-based games with a leaderboard.

GameSync limitations: state is fully public, in-memory only (lost on server restart), and the room can only hold as many concurrent WebSocket connections as the server allows. There's no database, no per-user identity, no admin panel.

When you need a real server app

Move beyond GameSync when your game requires any of:

The architecture that works

The Classroom Economy (and this Game Builder itself) use the same stack:

Node.js + Express better-sqlite3 WebSockets (ws) Google OAuth Docker + nginx
  • Express handles HTTP routes for the instructor admin API and student-facing pages
  • SQLite (via better-sqlite3) stores all persistent state: students, balances, rounds, jobs, bids
  • WebSockets push state updates to all connected browsers in real time
  • Google OAuth ties each browser session to a verified .edu email
  • nginx sits in front, handles HTTPS, and routes subdomains

The full stack runs in Docker Compose, which means you can develop locally and deploy on any Linux VPS with a single command.

How to build one

Step 1 — Clone the demo-kit and gut it

The Game Builder (apps/demo-kit-site/) is a working example of the full stack. The fastest path is to copy it and replace the HTML/JS frontend with your game, keeping the Express + SQLite + WebSocket skeleton.

cp -r apps/demo-kit-site apps/my-game
cd apps/my-game
# edit server.js, public/index.html

Step 2 — Design your database schema

Think about what needs to persist. A typical classroom game needs:

CREATE TABLE students (email TEXT PRIMARY KEY, name TEXT, section TEXT);
CREATE TABLE rounds (id INTEGER PRIMARY KEY, opened_at TEXT, closed_at TEXT);
CREATE TABLE submissions (email TEXT, round_id INTEGER, value REAL,
  PRIMARY KEY(email, round_id));
CREATE TABLE balances (email TEXT PRIMARY KEY, tokens REAL DEFAULT 0);

SQLite is fast enough for a class of 200 concurrent students and adds zero ops overhead — no separate database server to manage.

Step 3 — Build the API in Express

Each student action becomes a POST route. Each instructor action becomes a protected route (check req.session.user.email === ADMIN_EMAIL).

// Student submits a bid
app.post('/api/submit', requireAuth, (req, res) => {
  const { value } = req.body;
  const round = db.prepare('SELECT id FROM rounds WHERE closed_at IS NULL').get();
  if (!round) return res.status(400).json({ error: 'No open round' });
  db.prepare('INSERT OR REPLACE INTO submissions(email,round_id,value) VALUES(?,?,?)')
    .run(req.session.user.email, round.id, value);
  broadcast(); // push updated state to all WebSocket clients
  res.json({ ok: true });
});

Step 4 — Push state via WebSocket

Keep a broadcast() function that serializes the current game state and sends it to every connected client. Each client re-renders on every broadcast.

function broadcast() {
  const students = db.prepare('SELECT * FROM students').all();
  const subs = db.prepare('SELECT * FROM submissions WHERE round_id=?')
    .all(currentRoundId);
  const msg = JSON.stringify({ students, subs, round: currentRoundId });
  for (const [, ws] of clients) {
    if (ws.readyState === 1) ws.send(msg);
  }
}

Step 5 — Work with AI to write the hard parts

Describe what you want clearly and let Claude or ChatGPT write the routes, queries, and front-end rendering. The key is to describe the data model first:

Prompt that works well: "I'm building a classroom double-auction market in Node.js + Express + SQLite + WebSockets. Students post bids (buy) and asks (sell) for a single good. The instructor can open and close trading. At close, clear the market using the highest-price-first rule. Write the Express routes and SQLite schema for this."

Then iterate: "Now add a leaderboard endpoint", "Add a CSV download of all trades", "Add an instructor panel that shows bids and asks in real time."

Step 6 — Add authentication

Copy the Google OAuth flow from server.js in the Game Builder. It's ~80 lines that handles the OAuth redirect, email verification, session cookie, and optional .edu-only restriction.

Step 7 — Deploy with Docker Compose

The repo's docker-compose.yml already shows the pattern: a Node.js service, an nginx reverse proxy, and a shared data/ volume for the SQLite file. Add your new service alongside the existing ones.

my-game:
  build: ./apps/my-game
  environment:
    - BASE_URL=https://mygame.yourdomain.edu
    - SESSION_SECRET=${SESSION_SECRET}
    - GOOGLE_CLIENT_ID=${GOOGLE_CLIENT_ID}
    - GOOGLE_CLIENT_SECRET=${GOOGLE_CLIENT_SECRET}
  volumes:
    - ./data/my-game:/app/data

The Classroom Economy as a worked example

The app at apps/class-job-market/ is the most complete example in this repo. It includes:

  • Google OAuth login tied to a student roster
  • Token economy with a ledger of debits and credits
  • Job postings, bids, a weighted lottery draw, and automated wage payments
  • Flex-pass questions (students spend tokens to unlock bonus credit)
  • Instructor admin panel with round control, bulk grants, and CSV exports
  • A WebSocket-driven "Live Tracker" showing all student activity in real time
  • Unit tests in R (it's a Shiny app — the Node.js path above is the newer approach)

Read through apps/class-job-market/app.R to see how complex game logic can be organized. The newer Node.js approach (used by the Game Builder) is faster to iterate on and easier to deploy.

Tips from experience

  • Start with the data model. Get the SQLite schema right before writing a single route. Everything else flows from it.
  • One broadcast, one truth. Keep a single broadcast() function and call it after every write. Don't try to send partial updates — just send the whole state every time. SQLite reads are fast enough.
  • Instructor admin = query param or separate route. ?admin=1 checked against the session email is the simplest gate. No separate login needed.
  • Test with two browser tabs before involving students. Open the same URL in two tabs (one as student, one as instructor) to verify the WebSocket sync works.
  • Persist to SQLite early. In-memory state is fine for GameSync demos; the moment you care about losing data, write to SQLite. It's one line per query with better-sqlite3.
  • Let AI write the boilerplate, not the game design. Spend your time on the economics — what choices do students make, what information do they see, what are the incentives. The code to implement it is the easy part once you know what you're building.
Questions? The best way to get unstuck is to paste the relevant section of server.js into Claude and describe what you want to add. It can read the existing code and extend it in the same style.
